# 数据来源与真实性说明

本文档记录知识库中平台评分的**采集方式、时间与可信度**，供使用者判断数据的可用范围。

---

## 一、结论先行

知识库中的评分由**两部分**组成，报告页会明确区分：

| 类型 | 特征 | 可信度 |
|------|------|--------|
| 🟢 **实时抓取** | 带「来源链接」与「抓取时间」，可点击逐条核对 | 高 —— 直接来自平台公开页面 |
| 🟡 **离线估计** | 来源标注「离线估计，未联网核实」 | 低 —— 仅供参考，请以平台为准 |
| ⚪ **暂无数据** | 标注「暂无数据」 | — —— 不编造 |

**报告第五部分用三个色点明确标出每个平台属于哪一类**，不会让离线估计值混进实时数据里冒充可信值。

**实时抓取的数据**（豆瓣）来自平台公开页面，只读取**评分（score）与评价人数（count）**
两个客观数值，每条记录都记在 `data/ratings-atlas.json` 中，附 `sourceUrl` 与 `fetchedAt`。
可以用 `npm run ratings:verify` 校验全部记录是否来源可追溯。

截止最近一次抓取：**图谱 1040 条记录，全部具备来源链接**（覆盖 1040 / 1217 部作品）。
未抓到的 57 部会带上具体原因写进 `data/ratings-atlas.json` 的 `misses` 数组，
脚本运行结束时也会打印出来。原因分三类：

1. **豆瓣条目存在但尚无评分**（39 部）—— 条目确实在，只是**还没有人打过分**。
   这是新增冷门作品时最常见的情况（如《杀人者的记忆法》《马克斯之山》）。
   脚本把它单独报为「条目暂无评分」，与下面两类区分开，避免误判成"书不存在"
2. **豆瓣检索无结果**（7 部）—— 豆瓣的检索接口对书名写法敏感，
   系统已内置多策略检索（原名 → 去标点 → 去连接字 → 繁简转换 → 别名表 → 带作者），
   仍旧找不到的说明豆瓣确实没有该条目或书名差异过大
3. **详情页解析失败**（0 部）—— 可能被反爬或页面结构变化。出现时脚本会明确报出来，
   而不是悄悄记成"暂无数据"

前两类一律标注「暂无数据」，不会被伪装成实时值。
另有 2 部保留整理时的离线估计并显式标注。

> **繁体条目**：豆瓣上不少推理小说（尤其台版）只有繁体条目。
> 简繁归一表若缺字，这些书会被判定为「书名不匹配」而永远抓不到——
> 《11張撲克牌》《王與馬戲團》《巧克力遊戲》《贖罪奏鳴曲》都踩过这个坑。
> 现在表内覆盖 400 余组常用字，并有单元测试锁定（`normalizeTitle` 回归测试）。

## 二、为什么不是 100% 实时

### Goodreads：当前环境不可达

```
fetch https://www.goodreads.com/...  →  fetch failed（多次重试）
```

项目环境与整理环境的网络出口都访问不到 Goodreads（无公开 API，且直连超时）。
因此 Goodreads 一列**不做抓取**：42 部带有整理时留下的离线估计值
（`asOf: 2025-01`，无 `sourceUrl`），报告页会把它们与实时数据分开标注为
「🟡 离线估计：未联网核实，仅供参考」；其余 989 部标注「暂无数据」，
而不是填一个看起来合理的数字——按需求文档「不得编造」的要求，没有数据就说没有数据。

> 如果你在能访问 Goodreads 的网络里部署，可以自行扩展
> `scripts/refresh-ratings.mjs` 增加 Goodreads 的解析器（`web/js/core/ratings.js`
> 已经预留了 `parseWereadBook` 这类解析函数的写法与测试范式）。

### 虎扑：没有书籍评分体系

虎扑的评分主要覆盖影视与体育，图书条目缺少成体系的评分数据。
全部作品该列均为「暂无数据」，**不做不可靠估计**。

### 豆瓣：60 部未命中，其中 27 部是「豆瓣只索引了外文原版」

豆瓣的检索接口对书名写法敏感。系统已内置多策略检索
（原名 → 去标点 → 去连接字 → 繁简转换 → `data/search-aliases.mjs` 别名表），
1040 / 1217 部能实时命中有来源链接的条目。下面这张三分类表是**豆瓣正常时可得到的最后一次可信测量**（当时全库 1076 部、未命中 67 部）：

| 未命中原因 | 部数 | 含义 |
|------------|:----:|------|
| **豆瓣只索引到外文原版** | **28** | 检索确有结果，但全是日文/英文原版条目，**中文版的条目根本没进检索索引** |
| 条目存在但尚无评分 | 23 | 找到了条目，只是豆瓣上还没有人评价 |
| 检索无结果 | 16 | 换遍关键词也找不到可匹配的条目 |

> ⚠️ **这张表没有按最新一次运行刷新，是有意的。** 本轮抓取时豆瓣改为返回
> `HTTP 403 登录跳转页`（与之前的 429 限流不同），检索接口对**所有**关键词都返回空，
> 于是脚本把大量原本属于「只索引到外文原版」「条目存在但尚无评分」的书
> 统统归进了「检索无结果」（最新一次运行得到 67 / 7 / 3，与上表差异极大）。
> 那个分布**反映的是被拦状态，不是豆瓣的真实索引情况**，因此不予采信、不予同步。
> 待访问恢复后重跑 `node scripts/show-misses.mjs` 再更新本表。
> 此期间「未命中」总数（当前 77 部）仍然可信，只有**原因分类**不可信。

另有 2 部保留整理时的离线估计值并显式标注。

#### 第一类是这一轮才看清的问题

早期这三种情况**都只报「暂无数据」**，看不出区别。于是有一批书长期显示
「暂无评分」，而真实原因是：豆瓣对不少日本作品只收日文原版条目。例如
松本清张《黑革的手帖》，搜「黒革の手帖」只会返回 1983 年新潮社的上下卷
（无人评分），而中文版的条目压根不在检索索引里。

这类未命中现在会写成——

```
《黑革的手帖》—— 豆瓣只索引到外文原版条目
（黒革の手帖〈上〉（1983）、黒革の手帖〈下〉（1983）），
未找到中文版评分；保持「暂无数据」
```

——把「这本书没人读」和「豆瓣没收录中文版」区分开。这个区别很重要：
前者说明数据已经到位、只是缺评分；后者说明**该换的是检索思路，不是继续等**。

> ⚠️ 需要留意的是：这类书的中文版是否真的出版过，本系统无法从豆瓣证实。
> 书目标题按整理时掌握的中文版信息录入，评分一栏如实留空。
> 若你发现某本书其实没有中文版，欢迎按「见底」标准把它从知识库里去掉。

#### 豆瓣详情页解析自检

豆瓣改版或被反爬时，会出现「所有书突然都变成暂无评分」这种**静默错误**：
图谱看起来正常，实际全库评分停止更新。用一条命令即可区分是解析器坏了还是被拦了：

```
npm run diag:douban            # 抓一个确定有评分的条目做自检
npm run diag:douban 1082154    # 或指定条目 id
```

它会打印 HTTP 状态、是否命中反爬特征、页面里所有与评分相关的原始片段，
以及解析器的实际输出，并直接给出结论。

## 三、抓取是怎么做的

### 数据流

```
data/books/*.json          知识库（书名、作者、出版年）
        │
        ▼
scripts/refresh-ratings.mjs
        │  1. book.douban.com/j/subject_suggest?q=<书名>   检索候选条目（JSON 接口）
        │  2. book.douban.com/subject/<id>/                 抓取详情页 HTML
        │  3. web/js/core/ratings.js                        解析评分与评价人数
        │  4. 取「评价人数最多且 ≥200 人」的版本作为代表
        ▼
data/ratings-atlas.json    实时评分图谱（每条带 sourceUrl + fetchedAt）
        │
        ▼
scripts/verify-ratings.mjs 校验：来源可追溯、量纲合法、跨平台不串台
        │
        ▼
scripts/apply-ratings.mjs  写回 data/books/*.json（只动评分字段）
```

### 命令

```bash
npm run ratings:fetch        # 全量抓取（1217 部，耗时较长），只写图谱不动知识库
npm run ratings:fetch:missing # 只抓图谱里还没有的书（新增作品后跑这个，几分钟）
npm run ratings:verify       # 校验图谱：来源、量纲、精度、跨平台串台
npm run ratings:apply        # 预演写回变更；加 --apply 才实际写回
npm run ratings:update       # 上面三步串起来（抓取用 --merge 保留既有记录）
npm run ratings:recheck      # 重查未命中条目，区分「真没有」与「检索词没写对」

# 定向补抓某一本
node scripts/refresh-ratings.mjs --book western-001 --merge --candidates 5
```

### 解析层的可靠性设计

抓取逻辑最容易腐烂的地方是**解析**（平台一改版就失效），因此：

- 解析函数全部集中在 [`web/js/core/ratings.js`](../web/js/core/ratings.js)，
  **不做任何网络请求**，可以用固定的 HTML 片段做单元测试
- 已覆盖豆瓣评分的多种页面结构（`rating_num` / `v:average` / `rating_people`）
- 反爬页面、登录墙、空页面一律返回 `null`，**绝不猜测分数**
- 评分超出 0~10 直接判定为解析失败，而不是照抄
- `scripts/test-core.mjs` 中有 10 项针对解析层与校验层的测试
  （豆瓣详情页结构、检索候选、其他版本列表、微信读书推荐值、跨平台串台检出，
  以及 87 项测试中的标题归一化与 `titleSkeleton` 等价判定）

### 版本选择策略

豆瓣上同一本书常有多个版本，评分差异可以很大
（例：《犬神家一族》冷门版本只有 48 人评价，而通行版 3659 人）。

系统的策略是：

1. 每个书名先按**标题优先**的顺序尝试多个检索关键词
   （原名 → 去标点 → 去连接字 → 繁简转换 → 去括号 → 最后才带作者）
2. 抓取最多 4 个候选版本的详情页
3. **若这一批里没有评价人数 ≥ 200 的版本，自动扩大候选池到 12 个再试一轮**
4. 优先选择达标版本中评价人数最多的那个
5. 若全都不达标，退而取人数最多的并标记 ⚠ 低样本
6. 把实际采用的版本名与年份写进 `ratings.douban.edition`，让读者知道看的是哪一版

> **为什么带作者的关键词排在最后**：检索「知更鸟」时，豆瓣第一条是哈珀·李的
> 《杀死一只知更鸟》（9.3 分、9 万人评价），而目标是尤·奈斯博的《知更鸟》。
> 只按"评价人数最多"挑选会把完全无关的书的高分写进知识库。
> 因此系统加了 `looksLikeDifferentBook()` 守卫：**作者对不上且标题差异明显的候选直接否决**，
> 并有专门的回归测试锁住这个事故。

### 防张冠李戴

`looksLikeDifferentBook()` 的判定依据：

| 情况 | 处理 |
|------|------|
| 标题归一化后完全相同 | 放行（可能是同书不同版本） |
| 标题是包含关系、作者也匹配 | 放行（如「首无·作祟之物」vs「首无作祟之物」） |
| 标题包含但长出很多、且作者对不上 | **否决**（《杀死一只知更鸟》事故） |
| 作者对不上（标题相同） | 视差异程度决定，倾向于否决 |
| 候选缺作者信息 | 放行（交给评分逻辑判断） |

书名归一化会去掉标点、繁体转简体（内置常用字映射表），
因此繁体条目（如《惡魔的手毬歌》）能与简体条目正确匹配。

## 四、抓取结果的实况

| 指标 | 数值 |
|------|------|
| 覆盖作品 | 1040 / 1217 部 |
| 全部记录具备来源链接 | ✅ 870 / 870 |
| 评价人数中位数 | 1,695 人 |
| 评价人数最多的一条 | 《嫌疑人X的献身》559,997 人 |
| 样本最少的一条 | 《旋转楼梯》12 人（已标记低样本） |
| 低样本条目（<200 人） | 116 部 |
| 平台分布 | 豆瓣 870 条 |

> 中位数从 3,090 人（全库 323 部时）一路降到 1,968 人，是因为后续几轮都在**定向补空白**：
> 先是冷门国家与薄弱流派（冰岛、丹麦、法医鉴识），再是华语原创与日本古典 / 现代新作。
> 这些书的中文读者本来就少，评价人数低至十几人。
> 这是「尽量收全」的必然结果，不是抓取质量下降——**样本量已如实标注**，
> 评分排序也用了贝叶斯收缩（见 README「按评分排名」一节），低样本条目不会靠
> 一个虚高的分数窜到榜首。

### 实时值 vs 离线估计的偏差

抓取后与原有的离线估计做了对比，**平均偏差 0.43 分**：

| 书名 | 离线估计 | 实时值 | 偏差 |
|------|:--------:|:------:|:----:|
| 十角馆事件 | 8.3 | 7.0 | −1.3 |
| 砂之器 | 8.8 | 7.8 | −1.0 |
| 八墓村 | 8.4 | 7.5 | −0.9 |
| 漫长的告别 | 9.0 | 8.1 | −0.9 |
| 九九神咒 | 8.0 | 7.1 | −0.9 |
| 嫌疑人X的献身 | 8.9 | 8.9 | = |
| 白夜行 | 9.2 | 9.2 | = |
| 无人生还 | 9.0 | 9.0 | = |

**规律**：热门畅销书的离线估计相当准（多家平台数据一致，容易记对），
而中腰部作品的离线估计系统性偏高 —— 这正是必须做实时抓取的理由。
现在知识库里的这些值已经是实时值。

## 五、评价摘要的处理

`summary` 字段（去剧透评价摘要）**不来自抓取**，全部来自整理者的归纳。原因：

- 抓取书评正文会引入剧透风险，而本系统的最高铁律是绝不剧透
- 摘要统一采用「多数读者认为…」「部分读者指出…」这类**归因式表述**，
  而不是把整理者的判断伪装成平台共识
- 所有公开文本在写入知识库前都会经过
  [`web/js/core/safety.js`](../web/js/core/safety.js) 的规则引擎扫描，
  命中高危规则的条目无法通过 `npm run check`

## 六、合规与礼貌抓取

- 只读取**评分与评价人数**两个客观数值，**不抓取书评正文**
- 默认 1.2 秒/次的请求间隔，单本最多抓 4 个候选版本
- 使用正常的浏览器 User-Agent，不绕过任何登录或反爬机制
- 抓不到就保持原值并明确报告，**绝不编造**
- Goodreads 无公开 API，脚本**不做抓取**，避免违反其服务条款

抓取频率建议：**每月至多一次**。评分是慢变量，没必要频繁请求。

## 七、书籍元数据的来源

非评分类字段（书名、作者、出版年、系列、国别）依据公开出版信息整理，
同样可能存在偏差，特别是：

- **首次出版年份**：不同版本 / 译本可能给出不同年份，本项目取首次出版年
- **系列归属**：跨系列或独立作品可能被不同来源归入不同系列
- **原名**：日文原名的汉字写法可能与部分中文资料不同

如发现错误，可通过网页「添加小说」页修改，或直接编辑
`data/books/` 下对应的 JSON 文件后运行 `npm run check` 验证。
