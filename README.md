# 诡计档案 · 推理小说诡计标签分析与推荐系统

> 在**严格禁止剧透**的前提下，对推理小说进行结构化诡计标签分析，并推荐诡计机制高度相似的作品。

本系统把 `docs/reqirments.md` 中的「推理小说诡计分析专家」提示词规范，工程化成了一个可部署、可扩充、**可验证**的网页应用：
- 🏷️ **70 个标签的完整体系** —— 诡计类 / 叙事类 / 场景类 / 动机类 / 氛围题材类 / **推理流派**
- 🛡️ **敏感模式** —— 一键隐藏全部标签与分析信息，只留书名、简介、评价，**连"这本书是密室"都不告诉你**
- 📚 **持续扩充的知识库** —— 覆盖日系本格 / 新本格、欧美古典与黄金时代、社会派 / 硬汉派、华语推理、韩国与欧洲大陆推理、当代犯罪与心理惊悚、间谍小说
- 🎯 **可解释的相似度推荐** —— 诡计类优先加权，相似度为绝对口径，「为什么推荐这本」全程可见
- 🚫 **可执行的反剧透防线** —— 规则引擎 + 字段门禁 + 输出前自检，未通过则**拦截导出**
- ✍️ **动态添加小说** —— 网页表单实时体检，也可导入 JSON 批量扩充
- 📡 **实时评分抓取** —— 豆瓣评分为真实抓取值（2487/3287 部），每条带来源链接与抓取时间，可逐条核对
- 🕰️ **时间纵深** —— 从 1900 年泉镜花到 2024 年白井智之，含战前捕物帐、变格派与文学源流
- 📄 **六段式报告** —— 严格对齐需求文档的输出结构，一键复制 Markdown / 导出 / 打印 PDF
- 📦 **零运行时依赖** —— 原生 ES Module + `node:` 内置模块，无 npm 依赖、无构建步骤
- ✅ **七道质量门禁** —— 数据体检、口径排除项回归、候选分诊回归、单元测试、模块图检查、视图层回归、后端 E2E

## 快速开始

### 方式一：带后端运行（推荐，作品可持久化共享）

需要 Node.js **18 或更高版本**，无需安装任何依赖。

```bash
node server/index.mjs
# 打开 http://127.0.0.1:8787
```

或使用 npm 脚本：

```bash
npm start                # 默认 127.0.0.1:8787
npm run dev              # 带 --watch 自动重启
node server/index.mjs --port 3000 --host 0.0.0.0
```

后端模式下，你在网页上新增 / 编辑的作品会写入 `server/data/books.json`，
**所有访问者共享同一份知识库**，并且在入库前会经过服务端的反剧透校验。

### 方式二：纯静态运行（无需后端）

任意静态服务器都行，两种零安装的选择：

```bash
python -m http.server 3000     # Python 标准库，无需 pip
npx serve .                    # 需要能访问 npm registry
# 打开 http://localhost:3000/web/
```

此时所有计算都在浏览器本地完成，新增的作品保存在 `localStorage`。

> 💡 其实 `node server/index.mjs` 同时就是一台静态服务器：
> 前端会探测 `/api/health`，探测不到就自动降级为本地模式。
> 所以只想本地看看效果的话，用方式一即可，不必另找静态服务器。

> ⚠️ **不要直接双击 `web/index.html`**。浏览器对 `file://` 协议下的 ES Module
> 有严格限制，页面会加载失败。请用任意静态服务器访问。

## 敏感模式（连标签都不显示）

系统有两套呈现模式，**开关常驻在页面右上角**，随时可切换：

| | 普通模式 | 敏感模式 |
|---|---|---|
| 书名 / 作者 / 出版信息 | ✅ | ✅ |
| 无剧透简介 | ✅ | ✅ |
| 平台评价与评分 | ✅ | ✅ |
| 阅读提示（观察维度） | ✅ | ✅ |
| **诡计标签** | ✅ | ⛔ 全部隐藏 |
| **推理流派** | ✅ | ⛔ 全部隐藏 |
| **匹配明细 / 相似度 / 共享标签** | ✅ | ⛔ 全部隐藏 |
| 标签筛选与标签云 | ✅ | ⛔ 不渲染 |
| 推荐理由 | 说明共享了哪些标签 | 换为中性文案（「阅读体验与本书相近」） |
| 报告第二部分 | 完整标签 | 「本节已按你的设置隐藏」 |

### 为什么需要敏感模式

普通模式展示的是「这本书**有哪些类型**的诡计」。对多数读者这是有用信息，
但有一类读者连这一点都不想知道——他们希望像逛书店一样，只看书名、简介和口碑。
敏感模式就是为他们准备的。

### 实现：两道防线，而不是"藏起来"

**第一道：呈现层闸门**（`web/js/core/sensitive.js`）

所有渲染与导出都必须经过 `gate*()` 系列函数。闸门开启时，它们在**结构上返回空数组**，
而不是"渲染后再隐藏"：

```js
// 正确：先过闸门，标签根本没进 DOM
const shown = gateRecommendations(recResult);
renderReport({ book, recommendations: shown.recommendations, options: { sensitive: true } });
```

顺序很关键：**先渲染再隐藏，标签已经进了 DOM**，用户「查看源代码」或复制页面仍能读到，
敏感模式就形同虚设。因此内部约定是「先闸门，后渲染」。

**第二道：CSS 兜底**（`html[data-sensitive='on'] [data-sensitive-hide]`）

即使某个视图漏了闸门，样式层仍会把带 `data-sensitive-hide` 的元素整体隐藏。

### 覆盖范围

敏感模式作用于：诡计分析、知识库、书籍档案、作品对比、关于本系统，
以及 **Markdown 复制 / .md 导出 / 打印 PDF** 三个出口——
导出的内容与你在屏幕上看到的一致，不会"屏幕上藏了、导出里还在"。

> 「添加小说」「标签体系」两个页面本身以标签为内容，敏感模式下会显示说明而不是标签。
>
> 视图层测试里有 **16 项专门针对敏感模式的断言**，逐条路由扫描 DOM，
> 确认没有标签类元素（`.badge-trick` / `.tag-chip` / `data-tag` …）
> 与匹配依据文案（「核心诡计同属」等）残留。

## 标签体系

标签分 **6 个类别**，共 70 个标签：

| 类别 | 数量 | 权重 | 说明 |
|------|:----:|:----:|------|
| 诡计类 | 14 | **3.0** | 需求文档规定的核心诡计标签，推荐第一优先级 |
| 叙事类 | 8 | 1.6 | 叙述结构与人称视角 |
| **推理流派** | **14** | **1.4** | **写法取向，见下** |
| 场景类 | 12 | 1.0 | 物理空间与地理环境 |
| 动机类 | 10 | 1.0 | 动机类型（只标类型，不指向具体人物） |
| 氛围题材类 | 12 | 0.5 | 风格与题材，兜底信号 |

### 推理流派：与诡计正交的第二维度

需求文档未定义这一维度，是本系统的扩展。它回答的是「这本书**属于哪一路写法**」，
与「这本书**有哪些诡计**」是两个正交问题——**社会派作品同样可以有密室**，
所以它单独成类，而不是混进诡计类。

| 流派 | 说明 | 收录 |
|------|------|:----:|
| `逻辑流` | 以严密推演驱动，线索公平摆明（奎因式） | 613 |
| `诡计流` | 以诡计机关本身为卖点（岛田庄司、卡尔式） | 745 |
| `本格正统` | 黄金时代范式：封闭舞台、有限嫌疑人、读者可参与 | 988 |
| `社会派` | 以案件追问社会结构与人性处境 | 324 |
| `刑侦派` | 以警方办案流程为主线 | 314 |
| `法庭派` | 法庭对抗、证据攻防、判决为核心舞台 | 75 |
| `法医鉴识派` | 以法医与鉴识科学推动破案 | 91 |
| `硬汉派` | 冷硬都市里的孤独侦探 | 71 |
| `心理悬疑派` | 记忆、认知偏差与心理博弈构成主要悬念 | 409 |
| `间谍派` | 情报机构与组织对抗 | 15 |
| `冒险派` | 解谜与追逃探险并行 | 125 |
| `日常之谜派` | 生活化小谜团，暴力程度低 | 97 |
| `后设派` | 对推理文体本身戏仿、致敬或拆解 | 145 |
| `变格派` | 气氛怪奇、知识炫学（战前日本推理） | 317 |

一部作品可同时归属多个流派（全库 2948 部为多流派标注），
因为「社会派 + 本格正统」这类组合本身就是有意义的检索维度。

> **没有「诡计类」标签的作品照样有推荐。** 按「只标注确凿成立的标签」的原则，
> 一批社会派、刑侦、法医鉴识、间谍类作品（如北欧冷案、《首席女法医》系列）
> 本就不该被贴上密室或叙述性诡计。若仍硬性要求「诡计机制高度相似」，
> 这些书的推荐结果在数学上必然是空的。因此 `recommend()` 会在
> **目标作品自身没有任何诡计类标签**时放宽该约束、同时取消 `noTrickCap` 压制，
> 并在 `trickGate` 里如实标注，由档案页与报告**明确写出**
> 「本次推荐不含诡计维度，仅依据流派/叙事/场景/动机/题材相似度」。
> 放宽只对这一类书生效——有诡计标签的书仍强制要求诡计重合。

权重设为 1.4：**高于场景与题材**（流派比"故事发生在哪"更有区分度），
**低于诡计与叙事**（不喧宾夺主，推荐仍以诡计机制为主轴）。
在报告里它作为「二、诡计标签」的**补充小节**呈现，
不占用需求文档规定的 2.1~2.4 编号，也不打乱一~六章节的固定结构。

这个维度是全链贯通的：**知识库筛选**（标签云按 6 类分组）、**添加/编辑表单**
（独立勾选组，编辑时正确回填）、**推荐加权**（`同属 X 写法`）、
**作品对比**（流派的独有/共享）、**报告输出**、**敏感模式**（整块闸门）都支持它。

> 数据层用独立的 `school` 字段而不是塞进 `tags`：两个维度的权重差 2 倍多
> （诡计 3.0 vs 流派 1.4），混在一个数组里会让归一化、统计与编辑回填全部错位。
> `normalizeSeedBook()` 会**自愈**混写的数据，服务端也会对混写返回 422。

## 知识库构成

全库 **3287 部**，覆盖 29 个国家与地区。日本推理是重点，并刻意做到了**从战前先驱到当代新作的时间纵深**：

| 维度 | 数量 |
|------|:----:|
| 作品总数 | 3287 部 |
| 作者总数 | **792 位**（按 `author` 字段去重） |
| 日本作品 | **1446 部**（239 位作者） |
| 收录 ≥ 3 部的日本作者 | **117 位** |
| 流派标注覆盖率 | 3283 / 3287（4 条为多位作家的推理中篇合集，作者栏记「×× 等」） |

### 日本部分的时间分层

**古典 / 战前**（`batch-20-jp-classic.json`，23 部）——明治至昭和初期的先驱与怪奇谱系：

- **捕物帐**：冈本绮堂《半七捕物帐》、久生十兰《颚十郎捕物帐》
- **本格先驱**：大阪圭吉《银座幽灵》、浜尾四郎《日本推理名作选》（作者本职是检察官）
- **变格 / 怪奇**：兰郁二郎、小酒井不木、梦野久作《瓶装地狱》、江户川乱步《帕诺拉马岛奇谈》
- **文学源流**：芥川龙之介《竹林中》《罗生门》《地狱变》、谷崎润一郎《秘密》《春琴抄》《钥匙》
  《痴人之爱》《疯癫老人日记》、泉镜花《高野圣僧》《草迷宫》、佐藤春夫《田园的忧郁》、
  森鸥外《高濑舟》、夏目漱石《心》、国枝史郎《神州纐缬城》

> 《竹林中》是全库唯一被标为「多重叙述源头」的作品——几份互相矛盾的证词各自自洽，
> 这种结构后来成了叙述性诡计的常见骨架，因此它虽然成书于 1922 年，仍进入推荐图。

### 超出名单的扩面：只收「确认是推理小说」的作品

名单内 129 位作者收全之后，继续沿**出版社的推理专门丛书**扩面。这里有一条硬口径：

> **可以扩充，但每一部都要能证明是推理小说。**

所以扩面收书走的是**图书馆编目数据**而不是出版社文案。2026-09 豆瓣整站 403、
扬州市图书馆 OPAC 因限流不可达之后，"取证"这件事并没有断——又开出三条可用来源
（**其中豆瓣 403 已于第 128 轮实测解除**，见「评分数据」一节）：

| 来源 | 给出的关键字段 | 本轮用途 |
|------|----------------|----------|
| **上海图书馆 OPAC（VuFind API）** | 作者索引／题名索引／ISBN 索引 + **完整 CNMARC**（题名、责任者、出版项、**主题词**、**中图法**、丛编、提要） | **按作者枚举的唯一可靠渠道**（`npm run shlib:scan`，见 §59） |
| **对外经贸大学图书馆 OPAC** | 题名主题 / 中图分类 / 丛编项 / **相关题名附注（原题名）** / 提要文摘 | 单条取证与补提要（`npm run uibe:verify`） |
| **重庆工商大学图书馆 OPAC** | 同上（汇文系著录，另含并列题名） | 主力取证 |
| **图书在版编目（CIP）数据** | **关键词**（如「推理小说-小说集-美国-现代」）/ 中图分类 / 内容提要 | 交叉取证 |
| 当当（分类页 / 商品页 AJAX 详情） | 出版社 / ISBN / 出版年 / 编辑推荐 / 内容简介 | **只作候选发现与版本核对**，不作题材判据 |

硬判据是这两项：

- **中图法分类号 `I247.56`** ＝ 中国当代侦探／推理小说；
- **学科主题（题名主题）**含「推理小说」「侦探小说」。
- **CIP 关键词**含「推理小说」——出版前置的在版编目数据，与上两项同属最硬的一档。

有这几项就是正面证据；查不到馆藏时才退回「推理专门书系 + 内容简介的谜面」双重判据，
并在该条的 `verification.source` 里**写明判据较弱**，不把弱证据混进强证据里。

> 当当**没有**中图法与学科主题，因此它**不能**用来判定题材；本项目对它的定位是
> "发现候选"与"核对版本"。它的分类页（侦探/悬疑/推理，`cp01.03.38`）可翻页枚举，
> 五种排序各给出不同的前 6000 条切片，是豆瓣不可用时最大的**候选来源**。

> **枚举渠道的可靠性排序（第 58 轮实测，别再把②③当成枚举）**：
> ① **中图法分类号整类枚举**（`npm run scan:clc`，索书号必须带 `*` 通配）——
> **唯一可靠**的整类枚举渠道；② **题名检索**——只可用于**验证已知书名**，
> 不可用于发现（它其实是字面宽松匹配，查《犬神家一族》会返回《李小龙:生活的艺术家》）；
> ③ **按作者枚举**（第一个馆的 `creatorSearch`）——退化成单字 OR 匹配，**不可用**
> （查「阿加莎·克里斯蒂」返回 74445 条，而全库只有 48136 条）。
> 完整证据见 `docs/collection-backlog.md` §58.2。

直接决定这件事做不做得成。此前几轮一直记着「作者枚举不可能」——那是**旧馆 OPAC** 的结论。
本轮重读了对外经贸 OPAC 的**检索表单源码**，发现症结所在：

```html
<input type="radio" name="field" value="title" checked>
<input type="radio" name="field" value="abstract">
<input type="radio" name="field" value="creatorSearch">
<input type="radio" name="field" value="publisher">
<input type="radio" name="field" value="isbnSearch">
<input type="radio" name="field" value="callNumberSearch">
```

`field` **只认表单里列出的这几个值**。传别的值（`subjectSearch`、`seriesSearch`、`clcSearch`…）
不会报错，而是**静默退化成「全库列表」**——上一轮之所以判定「作者枚举是 no-op」，
正是踩了这个：检索确实"成功"了，只是把 48136 条全库记录端了回来。

而 `field=creatorSearch` **真的可用**，且结果行**逐条带「主题词」分面**。
于是新工具 `scripts/opac-author-scan.mjs` 把这条链路打通：

```
node scripts/opac-author-scan.mjs --authors 横沟正史,江户川乱步,东野圭吾 --max 160 --out _dd/author-scan.tsv
# → 每行：作者 · 题名 · 责任者 · 行内主题词 · 出版者 · ISBN · bookId，逐作者追加写入，可断点续跑
```

### 多作者模型：`author` 是标签，`authors` 是统计口径（`batch-133`）

前几轮一直有一条硬口径：**「多作者作品不收」**——库内 1596 部的 `author` 字段里
含「、」这类分隔符的是 **0 条**，模型从第一天起就是「一本书 = 一位作者」。
但积压下来一批**已核实是推理小说**的书因此进不来，于是本轮把模型扩了：

```
author  : "马伊·舍瓦尔、佩尔·瓦勒"      ← 展示标签（列表/排序/搜索/报告读它）
authors : ["马伊·舍瓦尔", "佩尔·瓦勒"]  ← 统计口径（作者榜/同作者加成/多样性上限读它）
```

**为什么必须分成两个字段**：如果聚合逻辑去读 `author`，那「马伊·舍瓦尔、佩尔·瓦勒」
会被当成**一个叫这两个名字的第三人**——作者榜上多一个只有 1 本书的伪作者，
而真正的舍瓦尔与瓦勒**各自都少了这一本**，「同作者」推荐也会同时错三处。
归一化时按「、，,;；」拆分（**绝不拆「·」**，那是阿加莎·克里斯蒂、约翰·迪克森·卡尔的
名字本身），并且**幂等**——`normalizeSeedBook` 会被喂进已规范化的对象。

| 改动位置 | 内容 |
|----------|------|
| `web/js/core/seed.js` | 新增 `splitAuthors` / `authorListOf` / `sharedAuthor`；`normalizeSeedBook` 产出 `authors` |
| `web/js/core/engine.js` | 同作者加成、推荐理由、**作者多样性上限**全部改按署名列表计 |
| `web/js/core/store.js` | 搜索命中其余合著者（用「佩尔·瓦勒」也能查到合著的书） |
| `web/js/views/manage.js` | 表单一个输入框，多位作者用「、」分隔 |
| `server/index.mjs` | `/api/stats` 的 `topAuthors` 按署名列表计 |
| `scripts/check-data.mjs` | 校验 `authors` 是数组、无重复、**与 `author` 标签不脱节**；汇总行报「多作者条目 N 部」 |

本轮据此补入 **9 部**：合著 6 部（《埃及剧院谋杀案》《电话谋杀案》《吸血鬼凶杀案》
三种福尔摩斯续写、《死亡的样板》博尔赫斯与比奥伊·卡萨雷斯、
《失踪的消防车》舍瓦尔与瓦勒夫妇、《最后一枪》），
合集 3 部（《坦得里奇庄园谋杀案》《凶手总是回到犯罪现场.2》《三个嫌疑人》）。

**两处刻意的克制**：合集类 `authors` **只登记馆藏明确列名的人**——
《凶手总是回到犯罪现场.2》馆藏只说「等 11 位」并列名 6 位，就只写这 6 位；
《三个嫌疑人》馆藏只给主编姓名、未列各篇作者，`authors` 就只写主编一人。

### 收口核查：为什么"逐位审计"只能靠候选书名

这一轮本打算对名单上全部 124 位作者做一次可补量审计，把"没有明显缺口"这句话
变成可核对的证据。**结论是做不到自动枚举**，过程记录如下，免得以后重复尝试：

| 尝试 | 结果 |
|------|------|
| `subject_suggest?q=作者名` | 只返回一个**作者节点**（含 `/author/<id>/` 链接），不含作品 |
| 抓 `/author/<id>/` | 返回 2951 字节的 JS 反爬中转页（「载入中 …」），正文由脚本注入 |
| 抓 `/author/<id>/works` | 404，页面内容确认是「你想访问的页面不存在」 |
| `/j/author/<id>/works` | 404，服务端明确回 `has no attribute 'author'`——**该接口不存在** |

所以审计只能维持现在的做法：**人工凭知识列出候选书名，再逐个探测**。
这个做法的局限是显然的——它只能发现"我能想到的书名"，
想不到的作品就查不到。这一点必须写在这里，而不是含糊地宣称"已收全"。

## 反剧透机制（最高铁律的工程化落地）

需求文档规定：「任一项为『是』，则必须删除对应内容后重新输出。」
本系统不把这句当作君子协定，而是做成了六层可执行的机制：

| 层级 | 机制 | 实现位置 |
|------|------|----------|
| 1 | **字段级门禁** —— 字段被明确标记为公开 / 保密 | `web/js/core/safety.js` → `FIELD_POLICY` |
| 2 | **谜底保险库隔离** —— `vault` 下内容在所有出口被递归剥离 | `stripVault()`，渲染 / 导出 / API 三处调用 |
| 3 | **规则引擎扫描** —— 12 条规则、30 条正则，覆盖 6 类风险 | `SPOILER_RULES` |
| 4 | **合法表述白名单** —— 「找出凶手是谁」「不剧透」等豁免 | `SAFE_PHRASES`（17 条） |
| 5 | **输出前自检** —— 5 条清单逐条判定，未通过则拦截复制/导出/打印 | `runSelfCheck()` |
| 6 | **服务端第二道防线** —— 入库前重跑同一套规则，不合格返回 422 | `server/index.mjs` → `validateBookPayload()` |

**风险等级**分为四档，命中即给出片段、风险类别与修复建议：

- ⛔ **高危** —— 断言了凶手身份 / 真相结局 / 手法实现 / 破解方式 → **阻止提交与导出**
- ⚠️ **可疑** —— 出现暗道、定时装置、身份调换等技术细节 → **阻止提交，需人工确认**
- ❓ **待确认** —— 需要人工判断的边界表述
- ℹ️ **提示** —— 不构成风险

规则覆盖的 6 类风险：`凶手身份`、`真相结局`、`手法答案`、`诡计破解`、`动机泄露`、`跨作品泄底`。

**知识库自带体检**：`npm run check` 会对全部作品跑一遍扫描并输出报告。

```
  ✓ 体检通过
    全部公开字段未检出高危泄底表述，字段结构与字数均符合规范。
```

## 按评分排名

知识库页的「按评分排名」是一个**与标签完全独立的维度**：标签只负责**筛选**，
排序负责**排名**，先筛后排，所以选了任意标签之后依然可以按评分排名。

排序方式共 7 种，其中三种与评分相关：

| 排序 | 口径 |
|------|------|
| **按评分排名（含样本量加权）** | 默认榜单口径，见下 |
| 按原始评分 | 直接用平台分数，不做任何处理 |
| 按评价人数 | 样本量排序，用来看「哪些书最多人读」 |

### 为什么默认榜单要加权

直接比原始分会造成排行榜最常见的失真——**用一个随时会变的数字冒充榜单**：

| 作品 | 原始分 | 原始排名 | 加权排名 |
|------|:------:|:--------:|:--------:|
| 《犬滩歌谣》 | 8.6（**26 人**） | #26 | **#167** |
| 《武士道十六岁》 | 8.6（**38 人**） | #27 | **#153** |
| 《死亡从天而降》 | 8.3（**41 人**） | #51 | **#165** |

26 个人打出的 8.6 分，和 17 万人打出的 9.0 分不是同一种数字。
因此默认榜单用**贝叶斯收缩**把分数按票数往全库均分（7.51）拉：

```
加权分 = (v / (v + 200)) × 该书分数 + (200 / (v + 200)) × 全库均分
```

票数 `v` 越少拉得越多；票数上到几百之后，加权分与原始分几乎一致，
不影响正常条目。门槛 200 与抓取脚本的 `--min-votes` 保持同一口径。

### 界面上的诚实标注

- 卡片上的评分**一律附带评价人数**（`豆瓣 9.0（17.1万人）`）——
  只给分数会让人误以为不同样本量的分数同等可靠
- 评价人数不足 200 的条目标 **⚠**，鼠标悬停提示「评价人数偏少，分数稳定性差」
- 只有按评分/人数排序时才显示名次角标 `#1 #2 #3…`——
  按书名排的时候标名次是噪声

> 加权**只影响排序**，不修改任何数据：原始分数、评价人数、来源链接
> 都保持平台原值，报告页展示的也是原值。想按原始分看，切换「按原始评分」即可。

## 推荐算法

需求文档的推荐逻辑是：

> 优先匹配「诡计类」标签重合度，其次匹配「叙事类」与「场景类」，
> 确保推荐作品在**诡计机制层面**高度相似。

### 类别权重

| 类别 | 权重 | 说明 |
|------|------|------|
| 诡计类 | **3.0** | 第一优先级，决定推荐的主排序 |
| 叙事类 | 1.6 | 第二优先级 |
| 场景类 | 1.0 | 第三优先级 |
| 动机类 | 1.0 | 辅助信号 |
| 氛围题材类 | 0.5 | 仅作兜底（系统扩展类别，需求文档未定义） |

### 得分构成

```
score = 0.62 × 加权重合度     共享标签权重之和 ÷ 目标作品标签权重总量
      + 0.24 × 加权杰卡德     整体标签画像的相似程度（抑制标签堆砌式伪相似）
      + 0.14 × 稀有度加权     共享冷门标签比共享常见标签更有信息量
      + 领域加成             同作者 +0.05 / 同流派 +0.02

相似度% = score ÷ 理论上限   理论上限 = 与该书标签配置完全相同时的得分
```

**百分比是绝对口径**，不是"候选中最高分 = 100%"。后者会让多本书并列 100%，
让读者误以为系统认为它们同样相似。绝对口径下的实测参考值：

| 对比 | 相似度 | 分档 |
|------|:------:|------|
| 《无人生还》×《狱门岛》 | 89% | 高度相似 |
| 《点与线》×《奇想，天动》 | 90% | 高度相似 |
| 《嫌疑人X的献身》×《白夜行》 | 80% | 高度相似 |
| 《无人生还》×《Y的悲剧》 | 64% | 较为相似 |
| 仅场景相近、诡计无重合 | 通常 < 40% | 风格相近 |

分档阈值：≥75% 高度相似 · ≥58% 较为相似 · ≥40% 风格相近 · 其余参考推荐。

### 领域约束

- **诡计类零重合的候选默认不推荐** —— 直接排除并说明原因，而不是勉强凑数
- **目标作品自身没有诡计类标签时自动放宽** —— 此时「诡计机制高度相似」在数学上
  无解（交集必为空），若仍强求则这类书永远是 0 推荐。放宽的同时取消 `noTrickCap`
  压制（否则所有候选的绝对相似度会被统一压低 38%），并在返回值 `trickGate` 中
  标注 `relaxed`，由档案页与报告**明确写出**「本次推荐不含诡计维度」。
  配置项 `relaxTrickOverlapWhenUntagged: false` 可关掉这一放宽。
  **放宽只对无诡计标签的书生效**，有诡计标签的书仍强制要求诡计重合
- **背景标签剔除** —— 出现频率 > 70% 的标签（如全库 90% 的书都有的「本格解谜」）
  不参与杰卡德计算，否则会把所有作品都拉得一样像
- **多样性控制** —— 同一作者最多推荐 2 本，同系列续作默认排除
- **用户自建条目默认不参与公共推荐** —— 避免个人录入数据污染结果
- **理由由真实共享标签生成** —— 推荐理由不可能出现「凭空相似」，且理由文本本身也要过反剧透校验

### 可解释性

「作品对比」页与报告页的「匹配明细」会展示每个类别下**共享了哪些标签、缺失了哪些标签**，
你可以直接核对算法给出的结论是否站得住。

## 数据格式

每部作品是一个 JSON 对象。完整 Schema 见 [`docs/data-format.md`](docs/data-format.md)，摘要：

```jsonc
{
  "id": "western-001",                 // 唯一标识，^[a-zA-Z0-9._-]{1,64}$
  "title": "无人生还",
  "originalTitle": "And Then There Were None",
  "author": "阿加莎·克里斯蒂",
  "authorEn": "Agatha Christie",
  "genre": "本格推理",
  "firstPublished": "1939",             // 作品首次出版年（原作年）；核不到就留空
  "editionYear": "2020",               // 本库所引版本的出版年（中译本年版）；中文原创留空
  "series": "",                        // 空字符串表示非系列作品
  "detective": "",
  "country": "英国",

  "tags": ["closed-circle", "isolated-island", "nursery-rhyme", "..."],  // 只能用标签字典中的 id

  "school": ["orthodox-school", "trick-school"],   // 推理流派：独立维度，与 tags 正交，可多个

  "safeSummary": "……",                 // 无剧透简介，≤ 100 字（硬性上限）

  "recommendationReason": "",          // 留空则由算法自动生成

  "ratings": {                         // douban/hupu/goodreads 三键必须存在
    "douban":     { "score": 9.0, "count": 200000, "asOf": "2025-01", "summary": "……" },
    "hupu":       { "score": null, "count": null, "asOf": null, "summary": "暂无数据" },
    "goodreads":  { "score": 4.28, "count": 1300000, "asOf": "2025-01", "summary": "……" }
  },

  "readingTips": {
    "suitableFor": ["喜欢封闭空间群像案件的读者"],
    "watchFor": ["童谣文本与事件发生的先后顺序"],   // 只写观察维度，不写答案
    "warning": "……"
  },

  // 谜底保险库：永远不输出到任何界面、报告或导出文件
  "vault": { "culprit": "", "coreTrick": "", "ending": "", "notes": "" }
}
```

**新增数据的方式**：

1. **网页录入**（推荐）—— 「添加小说」页填写，实时体检，提交即入库
2. **导入 JSON** —— 知识库页「导入 JSON」按钮，支持批量
3. **直接编辑数据文件** —— 往 `data/books/` 加 `batch-NN-<slug>.json`（必须是数组），
   然后在 `web/js/core/seed.js` 的 `SEED_FILES` 中登记（静态模式需要；后端模式自动读取）

改完数据后务必运行：

```bash
npm run check            # 反剧透体检 + 结构校验
npm test                 # 单元测试
npm run build            # 一键跑完上面两步并生成 manifest
```

| `npm run apply:tricks` / `:write` | 把**人工复核过**的诡计标签写进数据，并把命中原文抄进 `verification.source` 供日后回查。默认干跑 |
| `npm run backfill:edition2` / `:apply` | 用**上海图书馆**回填 `editionYear`（题名与作者双重吻合、且上图仅一版才填），补第一个馆没找到的那批 |
| `npm run ctbu:scan -- --keywords 探案,密室 --out _dd/ctbu-scan.tsv` | **第二馆（重庆工商大学）关键词枚举**：题名检索 + 逐条取详情页看学科主题词。⚠️ 该馆**关键字只按题名匹配**（按作者名查返回 0），且**不支持分类号检索** |
| `npm run backfill:edition` / `npm run backfill:edition:apply` | 给**引进作品**回填 `editionYear`：按题名到第一个馆查、**必须作者吻合且该馆仅此一版**，填了就把著录原文写进 `verification.editionYearSource`。默认预演，`--apply` 才写盘（定期落盘，可中断续跑） |
| `npm run audit:edition` | **复核**已回填的 `editionYear`：要求**作者与题名同时吻合**（短题名要求完全相等）。第 58 轮 224 条复核出 5 条「只作者吻合」，其中 1 条是真错（填成了同系列的另一本书），已撤回 |
| `npm run fix:genres` | 把体裁归一到规范列表（原措辞保留在 `genreDetail`），清掉会变成「其他」的值 |
| `npm run series -- --from-book "<书名>"` | **枚举一整套丛书**：从书籍详情页找到「丛书」链接，列出该丛书全部书目并标出哪些未收（`--out` 可导出待办队列） |
| `npm run gen:series -- --series <id> …` | 按丛书批量生成批次文件（不代拟情节，只按书名陈述收录篇目） |
| `npm run audit:offline` | **不联网**的质量体检：梗概过短、缺 warning、有系列却没写主角、标签过少 |
| `npm run report:authors` | 生成 `docs/名单作者收录清单.md`：逐位列出名单作者在库的全部作品，**交给你核对缺口**（因为作者书目无法自动枚举） |
| `npm run diag:access` | 豆瓣连通性诊断：条目页与丛书页分别探测，区分「被限流」与「页面改版」 |
| `npm run atlas:rebuild` | 从知识库中已写入的溯源字段重建评分图谱（图谱被误覆盖时用） |
| `npm run fix:merge-ledger` | 依据合并台账回填 alternateTitles 与溯源，并报告无法自动恢复的标签缺口 |

`npm run build` 会依次执行七道质量门禁，任一失败即中止：

```
▸ 知识库反剧透体检              ✓ 体检通过（3287 部）
▸ 口径排除项回归（纯恐怖/间谍）  ✓ 3287 部无一越界
▸ 已分诊候选 · 不收／待核不回流   ✓ 748 条无一条回流进库
▸ 核心逻辑单元测试              ✓ 117 项全部通过
▸ 前端模块图与语法检查          ✓ 全部模块可加载
▸ 视图层回归测试（真实执行）    ✓ 通过 151 项，失败 0 项
▸ 后端 API 端到端测试           ✓ 通过 49 项，失败 0 项
```

> **第二道「口径排除项回归」是补上的一次教训**：用户口径是「**纯恐怖、纯间谍不收**，泛推理收」，
> 但这条边界原先只写在 `docs/collection-backlog.md` 的自然语言里，**机器读不到**——
> 于是台账里早已写明「勒卡雷是公认的纯间谍小说，按用户口径从严排除」的
> 《锅匠，裁缝，士兵，间谍》《史迈利的人马》，以及被列为「两馆确实没有」的麦家
> 《风声》《解密》《暗算》，后来又从别的馆藏批次被收了进来，在库里躺了很久，
> 直到手工复核流派标签才被发现。现在结论落在 `data/exclusions.json`，
> 由 `scripts/check-exclusions.mjs` 每次构建时核对：**排除项一旦回流即构建失败**，
> 口径漂移从此是一次红灯，而不是一次人工回忆。

> **视图层回归测试**是这套门禁里最有价值的一道：它在自研的最小 DOM
> （`scripts/lib/minidom.mjs`，仅依赖 `node:` 内置模块）里**真实执行**前端视图，
> 逐条路由渲染一遍，并模拟点击、切换、跳转等交互。
> 页面级故障（路由写错、视图选了不存在的节点、模板渲染抛异常）都能在这里被抓到，
> 而不必等到打开浏览器才发现白屏。

> `ratings:fetch` 需要外网（本仓库的抓取走 Node 内置 `fetch`，不依赖任何第三方包）。
> 脚本只抓取**评分与评价人数**，不读取书评正文，因此不会引入剧透。
> 对 Goodreads 与虎扑**不做抓取**（前者无公开 API，后者书籍评分体系不完整），
> 避免违反服务条款与产生不可靠数据。

> 下面只留最小可用版本。

### 方案 A：纯静态托管（最简单）

把 **`web/` 和 `data/` 保持同级**一起上传到 GitHub Pages / Vercel / Netlify / 对象存储 + CDN。

⚠️ **不能只发布 `web/`**：`web/js/core/seed-files.js` 用相对路径静态 import
`../../../data/books/batch-*.json`，`data/` 缺席时知识库会是空的。
Netlify / Vercel 的 Publish directory 要填**仓库根目录**，不是 `web/`。

前端会自动探测 `/api/health`：探测失败就降级为本地模式。
此方案下所有功能可用，只是新增的作品保存在访问者自己的浏览器里。

### 方案 B：带后端部署（推荐）

```bash
# 服务器上（需要 Node.js 18+，无需 npm install）
PORT=8080 HOST=0.0.0.0 node server/index.mjs
```

用 systemd / pm2 / Docker 常驻，前置 Nginx 或 Caddy 做 HTTPS 反向代理：

```nginx
server {
    listen 443 ssl http2;
    server_name your-domain.com;

    ssl_certificate     /etc/letsencrypt/live/your-domain.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/your-domain.com/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:8787;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

此方案下知识库**共享且持久化**，并额外获得服务端反剧透校验。

### 无需数据库

用户提交的数据以 JSON 文件保存在 `server/data/books.json`，
采用**原子写入**（先写临时文件再 rename）+ **进程内串行队列**，避免并发损坏。
作品量级在数千条以内完全够用。数据目录已被 `.gitignore` 忽略，不会误提交。

## 重复条目治理

知识库是**分批写入**的，不同批次各自独立向豆瓣检索、独立写标签，于是同一部作品
可能被收成两个条目——**书名不同，所以「书名重复」检查抓不到**。这类重复会同时污染三件事：

1. 「作品总数」与「按作者收全」的进度被虚高；
2. 推荐结果里可能出现同一部书的两个条目（「每位作者最多 2 部」拦不住）；
3. 同一部书的标签被拆到两条记录上，重叠度计算偏低。

最近一轮做过一次全库排查，**合并了 24 组重复条目**（当时 926 部 = 合并前 950 部 − 24 组）。
合并后全库不再有重复：

```
npm run audit:duplicates     # 闸门：发现重复即退出码 1
npm run fix:dups             # 预演：列出保留哪条、删哪条、标签并集变化
npm run fix:dups:apply       # 执行，并写台账 + 写后自检
```

判定规则只有两条，且**闸门与修复工具共用同一套实现**（`scripts/lib/dup-rules.mjs`）：

- **原书名归一化后完全相等** —— 负责「异名同书」。《活尸之死》与《生尸之死》同为
  《生ける屍の死》；《球形的荒野》与《一个背叛日本的日本人》同为《球形の荒野》。
- **中文书名归一化后完全相等**，且作者可视为同一人。

> 早期版本还用了一条「原书名互为包含」，结果把同一系列的相邻各卷
> （《巷说百物语》/《后巷说百物语》、《思考机器探案集之幽灵汽车》/《…微笑的上帝》、
> 《连续"杀人鬼"青蛙男》/《…噩梦再临》）大批误判成重复——闸门报 34 组、其中 10 组是误报，
> 报告失去可信度后被整体忽略，真重复反而长期积压。**闸门必须只报能修的问题**，
> 这条规则因此被删掉，并由 `scripts/test-core.mjs` 锁住。

### 异名同书：另一版书名不会被丢掉

合并时落选那一版的中文书名会进入 `alternateTitles`。**搜索会一并命中，详情页会展示**
（「又名」一行），所以用旧译名或台版名来查照样找得到：

| 主条目 | 又名 |
|--------|------|
| 活尸之死 | 生尸之死 |
| 莫尔格街凶杀案 | 莫格街凶杀案 |
| 血腥的收获 | 红色收获 |
| 8的杀戮 | 8的杀人 |
| 球形的荒野 | 一个背叛日本的日本人 |

### 合并做了什么、不做什么

| 字段 | 处理 |
|------|------|
| `tags` / `school` | 取**并集**，并按 `tags.js` 的规范顺序重排 |
| `ratings` | 逐平台取有分者；两边都有分时取评价人数多的 |
| 原作名 / 首版年 / 系列 / 侦探 | 单边有值时互相补齐 |
| `alternateTitles` | 落选一版的书名保留下来 |
| `safeSummary` / `readingTips` | **一律保留主条目原文，绝不自动拼接**——梗概是人工撰写并过了泄底闸门的，自动合并会产生未经审核的文本 |
| `vault` | 两侧必须全空才允许合并，否则跳过并报告（防止把私密数据卷进来） |

主条目按「中文读者实际看到的那一版」选：先看豆瓣评价人数，再看字段完整度。
《球形的荒野》(2,716 人) 因此胜过《一个背叛日本的日本人》(1,853 人) 作主条目。

### 两个踩过的坑（都由脚本闸门锁住）

- **原作名被填成选集名**。《思考机器探案集》四卷都写了 `The Thinking Machine`——那是
  整套选集的名字。按原作名判重会把四卷并成一卷。现在三条以上且书名互不相同会被
  判为「疑似选集名」，交人工核对（`npm run audit:origtitle`）。
- **赢家所在文件没被写回**。早期版本的合并脚本只在「这个文件删掉过记录」时才落盘，
  于是只当赢家、一条都没删的文件被整体跳过——赢家拿不到标签并集与溯源，
  脚本却照样报合并成功。现在改为按「记录是否被改写」判断，并且**写完之后回读磁盘自检**，
  确认每条赢家都带上了 `mergedFrom`。

### 复核机制

`npm run ratings:recheck` 会重新核查所有「未命中」条目，用**多种检索口径**
（中文书名 / 原书名 / 书名+作者 / 去虚词写法）逐一探测，并区分三种结局：

| 结局 | 含义 |
|------|------|
| ✓ 有可用候选 | 之前判错了，可以补抓 |
| ? 有条目但被守卫否决 | 需要人工判断（可能确实是另一本书） |
| ✗ 多种口径均无结果 | 确实检索不到 |

> 这个脚本是被一次真实事故逼出来的：早期有 42 部被判为「豆瓣上没有」，
> 复核后发现绝大多数并非不存在，而是**我们用来检索的中文书名不对**
> （译名不一致、繁体/日文写法、只有外文原版条目）。
> 把「搜不到」当成「不存在」，是这类数据整理里最容易犯、也最难自查的错误。

系统严格遵循需求文档「不得编造」的要求：没有把握的一律写 `暂无数据`，
而不是填一个看起来合理的数字；评分只保留一位小数，不写假精确值。
**实时抓取的记录必须同时带 `sourceUrl` 与 `fetchedAt`**，
否则 `ratings:verify` 会直接判为「来源不可追溯」并让整条流水线失败。

需要更新数据时：

```bash
npm run ratings:update      # 抓取 → 校验 → 写回，一条命令
npm run ratings:fetch       # 或只抓取，不动知识库
npm run ratings:verify      # 单独校验图谱来源是否可追溯
```

完整的采集方式、版本选择策略、与离线估计的偏差分析，见
[`docs/data-sources.md`](docs/data-sources.md)。

## 如何动态添加新小说

有三种方式，从简到繁：

### 方式一：网页表单（推荐，单人使用）

打开「**添加小说**」页填写即可。表单会**实时做反剧透体检**：

- 写了带剧透的内容 → 立刻标红并**阻止提交**
- 简介超过 100 字 → 阻止提交（需求文档的硬性上限）
- 未选「诡计类」标签 → 提示推荐质量会下降

标签区按 **6 个类别**分组呈现，其中「**推理流派**」是与诡计正交的独立维度，
可多选（例如同时勾 `本格正统` + `诡计流`）。
两个维度在数据里**分开存放**（`tags` 与 `school`），提交时由服务端校验：

- 流派 id 写进 `tags` → 422 拒绝
- 诡计 id 写进 `school` → 422 拒绝
- 未收录的 id → 422 拒绝

编辑既有作品时，两个维度都会正确回填，保存不会丢失任何一侧。

有「高危」项时提交会被拦截；只有「待确认」项时可以人工确认后入库，
但该条目之后会带 ⚠ 标记。

### 方式二：导入 JSON（推荐，批量迁移）

知识库页「**导入 JSON**」按钮，接受以下两种格式：

```jsonc
// 单个数组
[ { "id": "...", "title": "...", ... } ]

// 或带元信息的导出格式（「导出我的条目」生成的就是这种）
{ "format": "dftr-knowledge-base", "version": 1, "books": [ ... ] }
```

导入默认跳过 id 重复的条目，并在完成后报告「新增 / 跳过 / 失败」的数量。

### 方式三：直接编辑数据文件（推荐，团队协作）

1. 在 `data/books/` 新建 `batch-NN-<slug>.json`（内容是**数组**，命名必须符合 `batch-NN-<slug>.json` 规范）
2. 运行 `npm run gen:seed` 重新生成种子清单（**这一步是必须的**，浏览器端需要静态清单才能加载 JSON）
3. 运行校验：

```bash
npm run check     # 反剧透体检，会指出任何可能泄底的表述
npm run build     # 六道门禁全跑
```

> 种子清单 `web/js/core/seed-files.js` 是**自动生成**的，不要手工编辑。
> 它的作用是让「往 data/books/ 放一个文件」这件事自动生效，
> 而不需要去改任何源码。

字段规范详见 [`docs/data-format.md`](docs/data-format.md)。

> **关于用户自建条目**：通过网页新增的作品 `origin` 为 `user`，
> 且默认 `recommendable: false` —— 它们只作为你自己的参考，
> **不会参与他人的推荐结果**，避免个人录入的数据污染公共质量。

## 渲染约定

需求文档要求「标签用反引号包裹」，同时又给出了 `密室` `不在场证明` `叙述性诡计` …
这样一串并列标签。为了让最外层始终是一个**合法的 Markdown 代码段**，本系统的输出约定为：

```markdown
`密室` `不在场证明` `叙述性诡计`
```

即每个标签独立用反引号包裹，标签之间以空格分隔。这样在任意 Markdown 渲染器中
都显示为独立的标签样式，复制该代码段再次粘贴也不会被拆散。

## 常见问题

**Q：直接双击 `index.html` 打开是空白 / 报模块加载错误？**
A：`file://` 协议下浏览器禁止加载 ES Module。请用静态服务器访问（`npm start` 或 `npx serve .`）。

**Q：页面顶部显示「本地模式」是什么意思？**
A：说明没有检测到后端。所有数据保存在你的浏览器 `localStorage` 中，换浏览器或清缓存会丢失。
运行 `npm start` 即可切换到「服务器模式」。

**Q：我添加的小说为什么不参与别人的推荐？**
A：用户自建条目默认 `recommendable: false`，只作为你自己的参考。
如需纳入公共推荐，编辑数据把该字段改为 `true`（管理员操作）。

**Q：报告里的评分看起来不太准？**
A：报告第五部分会用色点标出每条评分属于「🟢 实时抓取」还是「🟡 离线估计」。
🟢 的那部分带来源链接与抓取时间，可逐条点开核对；🟡 的那部分是整理时的估计值，
仅供参考。要刷新实时值请运行 `npm run ratings:update`（需要外网）。

**Q：Windows 上 `npm start` 报「禁止运行脚本」？**
A：这是 PowerShell 的执行策略拦住了 `npm.ps1`，与本项目无关。
用 `node server/index.mjs` 直接启动即可（不走 npm，效果完全一样），
或执行 `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned` 放开当前用户。

**Q：如何增加新的诡计标签？**
A：编辑 `web/js/core/tags.js` 的 `TAGS` 数组，追加 `{ id, label, category, spec, desc, aliases }`。
所有页面、校验脚本与推荐算法会自动同步——这是标签的唯一事实来源。

**Q：能分析知识库里没有的书吗？**
A：「诡计分析」页切到「输入新作品」，填入书名与无剧透梗概，系统会从梗概中推断候选标签
（带命中片段供你核对），确认后即可生成报告。此路径的推荐基于你确认的标签。

**Q：为什么某本书没有被推荐给任何作品？**
A：检查它是否被标了「诡计类」标签。系统默认要求候选与目标在诡计类至少共享一个标签，
否则不予推荐——因为需求文档要求推荐必须在诡计机制层面相似。
